# 07 — SDD and AI-DLS in IT CrudWorks

- **Status:** adopted 2026-11-11
- **Owner:** orchestrator
- **Applies to:** every agent and every change in this repository

## 1. Why this document exists

The exercise evaluates more than a working application. It evaluates how the
candidate thinks, structures work, uses AI, and defends decisions. This project
therefore treats the **development process as a deliverable**:

- **SDD (Spec-Driven Development):** behavior is defined in specs before code.
- **AI-DLS (AI-Driven Development Life Cycle):** agents participate in every
  phase, but each phase has an artifact, an owner, and a verification gate.

The result is a traceable chain from the exercise PDF to a test that proves a
status code.

## 2. The AI-DLS loop used here

```
Intent        → Spec        → Plan         → Tasks        → Red test
(why)            (what)        (how)          (next step)     (proof)
     ↑                                                          ↓
Learning      ← Evidence    ← Validation   ← Implementation ← Green
(retro)          (AI log)      (tests/demo)    (code)
```

| Phase | Artifact | Owner | Gate to leave the phase |
| --- | --- | --- | --- |
| Intent | `docs/00-brief.md`, user story | Orchestrator | Scope and deadline agreed |
| Spec | `specs/NNN-*/spec.md` | Architect | Testable acceptance criteria |
| Plan | `specs/NNN-*/plan.md` | Architect | Layers, contract, test strategy |
| Tasks | `specs/NNN-*/tasks.md` | Orchestrator + implementers | Ordered, small, owned |
| Red | Failing test | Implementer | The test fails for the right reason |
| Green | Minimum implementation | Implementer | The test passes |
| Validation | Build, tests, manual check | Implementer + QA | Real output captured |
| Evidence | `docs/ai/NNN-*.md`, review, QA report | Every agent | Claims match artifacts |
| Learning | Change log, retro note | Orchestrator | Next change is smaller |

This is the AI-DLS principle applied concretely: **AI accelerates each phase, but
never removes the gate between phases.** The model drafts; the engineer verifies;
the artifact records both.

## 3. Agentification

The team is intentionally small. Each agent owns one kind of risk and one set of
artifacts. The canonical definitions live in `agents/`; OpenCode copies are
generated by `scripts/sync-agents.ps1`.

| Agent | SDD role | Owns | Must not |
| --- | --- | --- | --- |
| Orchestrator | Phase owner | specs index, sequencing, traceability, delivery | Do specialist work silently |
| Architect | Spec + plan | `specs/*/spec.md`, `plan.md`, ADRs, contract | Write production code |
| Backend implementer | Red → green | Domain/Application/Infrastructure/Api + backend tests | Change the contract or architecture |
| Frontend implementer | Red → green | React app + frontend tests | Invent fields or endpoints |
| Reviewer | Validation | severity-ordered findings, verdicts | Fix the code |
| QA engineer | Evidence | test plan, E2E/API seams, seed, release evidence | Rewrite features |

**Rule:** an agent reads the spec, the relevant ADR, and the current code before
acting. An agent that cannot cite the spec does not implement.

## 5. How a feature is added

1. **Pick the requirement.** Find the `R-XX` row in `docs/04-requirement-traceability.md`.
2. **Write or update the spec.** Add a user story and Given/When/Then criteria.
   New scope outside the spec is rejected or added deliberately.
3. **Write the plan.** Name the layers, the contract, the tests, and the risks.
4. **Break it into tasks.** Each task has an owner, a dependency, and a test.
5. **Red.** Write the smallest failing test that proves the next criterion.
6. **Green.** Implement the minimum. Keep the dependency rule.
7. **Verify.** Run the real commands; capture output.
8. **Record.** Update the task status, traceability row, README if behavior or
   setup changed, and `docs/ai/`.
9. **Review.** The reviewer checks against the spec, not against taste.
10. **Close.** QA marks the spec `implemented` only when every criterion has
    evidence.

## 6. What is deliberately lightweight

- No spec tooling or DSL: Markdown in git is enough and reviews well.
- No separate product-owner agent: the orchestrator owns scope; the architect
  owns precision.
- No full RFC 2119 language: Given/When/Then and concrete status codes are more
  useful here.
- No ceremony for a one-line fix: a typo fix does not need a spec, but it still
  needs a test or a review note if behavior changes.

## 7. Anti-patterns this project rejects

| Anti-pattern | Why it is rejected |
| --- | --- |
| Code first, spec written afterwards to match | The spec becomes a description, not a decision |
| AI output merged without validation | The exercise evaluates critical thinking, not generation |
| "Tests pass" without captured output | Not evidence |
| Specs that restate the UI without acceptance criteria | Untestable |
| Agents editing outside their ownership | Merge conflicts and silent drift |
| Using AI to invent requirements | Scope creep with no traceability |

## 9. How to explain it in the interview

> "I used SDD to separate what the system must do from how it is built. The spec
> is the contract: acceptance criteria in Given/When/Then, an explicit API
> contract, and a task list. AI agents participate in every phase, but each phase
> has an artifact and a gate: a spec must be approved before code, a test must
> fail before it passes, and every claim must have real output. That is the
> AI-DLS loop: intent, spec, plan, tasks, implementation, validation, evidence,
> learning. The repository is the audit trail."
